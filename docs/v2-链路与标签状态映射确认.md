## 1. 全景数据流

```
抖音/其他链接 + 标签（用户手机分享或 doubaosave 批量导入）
        │
        ▼
飞书多维表格「视频收藏表」＝唯一外部真相源
   列：链接 | 标签/标签2..标签5 | 处理状态(select) | work_id | 最后修改时间
        │  bridge_feishu_obsidian.py 常驻轮询（--watch，60s）
        ▼
   lark-cli base +record-list（用户身份，ndjson）
        │  filter-json 按「最后修改时间」增量 + record_id 双保险去重
        ▼
  DispatchStore（SQLite 队列：pending→queued→processing→终态）
        ├── 快轨A（秒级）：写 Obsidian 占位笔记 frontmatter status=pending
        └── 慢轨B（分钟级）：TokBrain 预检→confirm→ingest→obsidian/manifest
                 → 回填笔记正文+关键帧硬链接，status=processed
        ▼
   回写飞书「处理状态」列（仅状态变化时写）+ work_id
```

## 2. 链接与标签如何进入飞书表、由谁填充

| 列 | 写入方 | 内容 |
|---|---|---|
| `链接` | 用户手机分享 / doubaosave 导入 | 抖音短链或完整链接 |
| `标签`~`标签5` | 用户手动 / doubaosave 导入「标签」列 | 文本，可多列；doubaosave 写收藏夹层级路径（如 `夹A/子夹B`） |
| `处理状态` | **bridge 回写**（`writeback_feishu_status`） | select：待处理/处理中/已归档/需补件/失败 |
| `work_id` | **bridge 回写**（同上） | number：TokBrain 作品 id，便于排查 |
| `最后修改时间` | 飞书平台自动维护（updated_at 类型） | 增量轮询的过滤依据 |

**doubaosave v2 只写左半部分**（链接/标题/作者/来源/发布时间/标签），**状态三列由 bridge 负责**，两者以「链接」+「标签」衔接，互不冲突。

## 3. bridge 如何读取飞书表格（标签与状态）

代码：`Feishu` 类（`bridge_feishu_obsidian.py:264-500`），全部走 **lark-cli 用户身份**（自建应用未开 tenant scope）。

### 3.1 标签读取（`_row_tuple`，行 428-442）

```python
FS_TAG_COLS = ["标签","标签2","标签3","标签4","标签5"]   # 5 个文本列
# 对每行：逐列取文本，非空收集
tags = [v for col in FS_TAG_COLS if (v := self._text(fields.get(col)).strip())]
tags = " ".join(dict.fromkeys(tags))   # 合并 + 去重 + 空格连接
```

- **读的是 5 个 text 列**，合并成空格分隔字符串传给 TokBrain
- `_text()` 兼容 list/dict/None 单元格值（`bridge_feishu_obsidian.py:445-459`）

### 3.2 状态读取（不直接读「处理状态」列）

TokBrain 侧的**状态唯一权威是本地 `dispatch.db`**（`DispatchStore`），飞书「处理状态」列只是**回写镜像**：

```
dispatch 状态 → 飞书「处理状态」列（DISPATCH_TO_FEISHU_STATUS，行 103-110）
  pending        → 待处理
  queued         → 处理中
  processing     → 处理中
  processed      → 已归档
  needs_supplement → 需补件
  failed         → 失败
```

回写条件（`writeback_feishu_status`，行 979-1024）：
- 仅状态**变化**时回写（幂等、省接口额度）
- 跳过 `local-*` / `inbox-*` 本地来源（只回写真实飞书 record_id）
- 回写失败只记日志、下轮重试，不阻塞主流程

### 3.3 增量拉取（`get_updated_rows`，行 407-426）

```json
{"logic":"and","conditions":[["最后修改时间","isGreater","<游标>"]]
```
游标持久化在 `同步状态.json`，回退 300s 防时钟偏差；`filter-json` 语法不被接受时自动降级全量 + `record_id` 差分。

## 4. Obsidian 如何读状态与标签

Obsidian 不直接读飞书表，而是读 bridge 落盘的**笔记 frontmatter**（`bridge_feishu_obsidian.py:705-808`）：

| 阶段 | frontmatter 关键字段 | 说明 |
|---|---|---|
| 占位（快轨） | `status: pending` `tags: [合并标签]` `feishu_record_id` `work_id: null` | 路径 `{VAULT_NOTES}/{首标签}/{record_id}.md`，首标签按 `/` 展开多级目录（子夹缺失自动新建） |
| 回填（慢轨） | `status: processed` `work_id` `tokbrain_synced_at` | `merge_frontmatter` 只替换顶层键，保留原文结构 |
| 失败/需补件 | `status: failed/needs_supplement` + `error` | `mark_note_status` 保证笔记状态真实，不滞留 pending |

- **目录即标签**：`00收件箱/视频收藏/{首标签}/{record_id}.md`，首标签来自飞书第 1 个非空标签列
- **状态在 Obsidian 里看 frontmatter `status`**，与飞书「处理状态」列语义一致（同一状态机，见 pipeline-v2-plan 第 2.1 节）

## 5. 「分级标签」现状与缺口

**当前代码中没有"分级标签"概念**（全项目 grep 无"分级"）。现状是：

| 项 | 现状 |
|---|---|
| 标签载体 | 飞书 5 个 text 列（`标签`~`标签5`），读取时**合并去重、扁平化**，无层级语义 |
| 目录分级 | 首标签按 `/` 展开多级目录（2026-08-29 已实现）：`视频收藏/夹A/子夹B/`，缺失自动新建；其余标签在 frontmatter `tags` |
| 状态分级 | 「处理状态」5 档（select）即唯一分级体系 |
| 待确认项 | `pipeline-v2-plan.md` 第 8 节 #5：**"笔记标签分类维度：沿用飞书 5 个标签列，还是改用单一多选列？"** —— 仍未定 |

**若"分级标签"指飞书 5 列中约定的优先级/等级（如 标签=主题、标签2=重要级），当前读取逻辑不会区分语义**，全部合并。要做分级需要：

1. **明确飞书 5 列的语义约定**（如 `标签`=主题/收藏夹、`标签2`=优先级 ★/A/B/C）
2. `_row_tuple` 按列位置拆分处理（而不是全合并）：首标签进目录、指定列进 frontmatter 独立字段（如 `priority`）
3. 或采用 pipeline-v2-plan 备选：改单一多选列 + 单独「优先级」select 列

## 6. 与本会话 doubaosave 增强的关系

- doubaosave v2（`doubaosave Skill/source/`）把抖音收藏夹层级写入飞书「标签」列（如 `夹A/子夹B`）
- bridge 读取时首标签=`夹A` → Obsidian 笔记落 `00收件箱/视频收藏/夹A/`
- 子夹路径 `子夹B` 目前只存在于 frontmatter `tags`，不构成目录层级
- 若要 Obsidian 按「父夹/子夹」两级目录，需在 bridge 层拆分标签再定路径（属第 5 节"分级"改造范围）
