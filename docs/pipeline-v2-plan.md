### 实施中发现并修复的缺陷

**慢轨失败后笔记状态不更新**：队列已标 `failed`，但占位笔记 frontmatter 仍为 `pending`，用户在 Obsidian 里会误以为还在处理。
修复：新增 `mark_note_status()`，在 `needs_supplement` / `failed` 分支把状态与错误原因写回笔记 frontmatter。复测确认笔记显示 `status: failed` 并附 `error` 字段。

### 关键实现决策

- **笔记文件名用 `record_id` 而非标题**：快轨阶段还没有真实标题（预检未完成），用 record_id 才能保证路径在快轨就已固定、回填时不变。真实标题写在 frontmatter 的 `title` 里。
- **`merge_frontmatter()` 保留原有行顺序**：只就地替换顶层键、缺失时追加，避免破坏 manifest 自带的复杂 YAML 结构。
- **游标与已同步列表双保险**：增量过滤和 `record_id` 去重任一命中都不会重复处理。
- **单进程顺序执行两阶段也能达成解耦目标**：快轨先把所有新行的占位笔记写完，再进慢轨，Obsidian 侧已经立即可见，无需引入多进程复杂度。

## 1. 现状链路与瓶颈

```
手机分享 → 飞书多维表格（人工/自动化写入）
              ↓  bridge_feishu_obsidian.py 手动执行
          lark-cli base +record-list（用户身份，全量拉）
              ↓  逐行串行
          TokBrain 链接预检 → confirm → ingest → wait_job（阻塞，最长 10 分钟）
              ↓  处理完成才继续
          obsidian/manifest → 复制关键帧 → 写笔记
              ↓
          回写本地 同步状态.json
```

三个硬伤：

1. **串行阻塞**：`main()` 里 `process_link()` 内 `tb.wait_job()` 同步等待，一条视频卡住整批，`export_to_obsidian` 必须等它跑完。
2. **变更感知靠人**：脚本要手动跑，无自动触发。
3. **关键帧双倍占用**：`gather_keyframes()` 用 `shutil.copy2()` 把 `data/keyframes/**` 全量拷进 Vault 附件目录，同一份 JPG 磁盘上存两份。当前 24 张 / 2.93 MB，规模上去后线性翻倍。

## 2. 目标架构：双轨解耦

```
                  ┌──────────── 收件层 ────────────┐
抖音分享 ──────►  飞书多维表格（唯一外部真相源）
                          │
外部/导出数据 ─►  POST /api/integrations/v1/inbox/items（预留）─┘
                          │
              ┌───────────┴────────────┐
              │  变更感知：60s 增量轮询  │
              │  base +record-search    │
              │  filter 最后修改时间>游标 │
              └───────────┬────────────┘
                          │  record_id + 链接 + 标签
              ┌───────────┴────────────┐
              │      分派（Dispatcher）  │
              └───────────┬────────────┘
         ┌────────────────┼─────────────────┐
         ▼                                  ▼
  【快轨 A｜秒级】                    【慢轨 B｜分钟级】
  写 Obsidian 占位笔记                TokBrain 预检 → confirm
  frontmatter: status=pending         → ingest → 轮询 job
  链接/标签/record_id/时间                    │
         │                                  ▼ 处理完成（终态）
         │                            回填笔记正文 + 关键帧硬链接
         │                            frontmatter: status=processed
         └──────────► 各自独立、互不等待 ◄──────┘
                          │
                  回写飞书状态列（可选）
```

核心原则：

- **快轨不等慢轨**：占位笔记在收件后立刻落盘，用户在 Obsidian 里马上能看到"这条已收，正在处理"。
- **慢轨完成后回填而非新建**：笔记路径在快轨阶段就确定，回填只做内容覆盖 + frontmatter 状态迁移。
- **幂等键统一为 `record_id` + `aweme_id`**：任何一步中断重跑都不会产生重复笔记或重复处理。

### 2.1 状态机

| 阶段  | 笔记 `status`        | 飞书「处理状态」列 | 含义                        |
| --- | ------------------ | --------- | ------------------------- |
| 收件  | `pending`          | 待处理       | 占位笔记已写，TokBrain 未接单       |
| 已派单 | `queued`           | 处理中       | 已创建 import batch，预检中      |
| 处理中 | `processing`       | 处理中       | ingest job 运行中            |
| 成功  | `processed`        | 已归档       | 正文 + 关键帧已回填               |
| 需补件 | `needs_supplement` | 需补件       | 作者禁止下载，等待人工上传视频           |
| 失败  | `failed`           | 失败        | 预检失败/风控/链接失效，附 error_code |

终态：`processed` / `needs_supplement` / `failed`。`pending`/`queued`/`processing` 为非终态，重启后自动续跑。

设计要点：

| 项    | 规则                                                                            |
| ---- | ----------------------------------------------------------------------------- |

### 3.5 自动抓取的替代方案：用户触发式导出

自动化与人工之间的第三条路——**由人控制时机与范围，由脚本负责搬运**。

| 边界   | 自动抓取（否决） | 用户触发式导出（可行）           |
| ---- | -------- | --------------------- |
| 登录态  | 脚本持有/刷新  | 用户在自己浏览器里登录，脚本不碰      |
| 翻页遍历 | 自动翻完整个列表 | **不翻页**，只导出当前页面已渲染的内容 |
| 触发时机 | 定时或后台常驻  | 用户手动点击，一次一次           |
| 请求行为 | 模拟接口请求   | 只读 DOM 里已经展示出来的内容     |
| 规模   | 全量       | 用户自己决定，建议单屏几十条        |

**实现形式**（三选一，推荐第一个）：

1. **浏览器书签小工具（Bookmarklet）**：收藏夹页面点一下书签，把当前页链接复制成 JSON 到剪贴板，粘贴到本地文件或直接提交入站 API。零安装、零后端。
2. **用户脚本（Tampermonkey）**：在收藏夹页面注入一个「导出本页到 TokBrain」按钮，点击后 POST 到 `http://127.0.0.1:8001/api/integrations/v1/inbox/items`。
3. **本地中转文件**：用户手动复制页面文本 → 存成 `inbox-export.txt` → 本地脚本解析后提交。最土但最稳。

安全约束：

- 目标地址**只能是 `127.0.0.1`**，由本地 API 的 CORS 白名单把关（现已在 `app/config.py::_LOCAL_FRONTENDS` 维护）
- 单批仍受 ≤ 100 条限制，且入队后受全局并发 1、4–8 秒冷却、熔断 30 分钟约束
- 提交时 `rights_attested: true` 由调用方显式声明

这样既能"一键批量"省掉重复劳动，又不越界。**需要的只是你在页面上点一下。**

## 4. 诉求二：飞书表格变更感知

### 4.1 实测结论

```
$ lark-cli event list
application / approval / board / card / im / minutes / task / vc
```

**没有任何 bitable / base 相关事件**。`lark-cli event schema drive.file.bitable_record_changed_v1` 返回 `unknown EventKey`。事件总线当前 `Bus: not running`。

所以「订阅多维表格变更事件」这条路在当前工具链下不成立。

### 4.2 三条路径对比

| 路径        | 机制                                                      | 延迟  | 需要公网  | 红线冲突              | 结论                  |
| --------- | ------------------------------------------------------- | --- | ----- | ----------------- | ------------------- |
| **A 轮询**  | 定时 `base +record-search` 增量                             | 60s | 否     | 无                 | ✅ **本期实现**（满足分钟级要求） |
| B Webhook | 飞书自动化 → HTTP 请求到本地                                      | 秒级  | **是** | ❌ 违反「不得隧道/反向代理暴露」 | ❌ 否决                |
| C 事件订阅    | 官方长连接收 bitable 事件                                       | 秒级  | 否     | 无                 | ❌ 事件不存在             |
| D 推送中转    | 自动化 → 发飞书消息给机器人 → `event consume im.message.receive_v1` | 秒级  | 否     | 无                 | ⏸ 未来可选（实时性升级到秒级时再上） |

### 4.3 本期实现：定时增量轮询（A 路）

实时性要求确认为分钟级，因此**只做 A 路**。相比原推拉双轨方案，省掉飞书自动化配置、机器人建群、事件总线常驻三件事，复杂度大幅下降。

**飞书表新增列**（已确认可加）：

| 列名        | 类型                            | 用途                   |
| --------- | ----------------------------- | -------------------- |
| `处理状态`    | 单选：待处理 / 处理中 / 已归档 / 需补件 / 失败 | 状态可视化，人工一眼看进度        |
| `work_id` | 数字                            | 与 TokBrain 作品关联，便于排查 |
| `最后修改时间`  | 公式或自动化维护                      | **增量拉取的过滤依据**，避免全量扫描 |

**轮询循环（60 秒）**：

```
每 60s:
  cursor = dispatch.db 里记录的 last_sync_time
  rows = lark-cli base +record-search \
           --filter "最后修改时间 > cursor"  --as user
  for row in rows:
      if record_id 已处理: continue
      快轨 A: 写 Obsidian 占位笔记 → 入队 dispatch.db
      慢轨 B: 队列消费 → TokBrain 预检/confirm/ingest → 回填笔记
      回写飞书: 处理状态 / work_id
  last_sync_time = max(rows.最后修改时间)
```

要点：

| 项    | 规则                                              |
| ---- | ----------------------------------------------- |
| 增量依据 | 优先用 `最后修改时间` 过滤；该列未生效时自动降级为全量拉 + `record_id` 差分 |
| 幂等   | `record_id` 去重，重复扫描不会重复处理（见第 5.4 节）             |
| 失败续跑 | 非终态条目下次循环自动接管；`failed` 需人工确认后重投，避免风控期反复撞墙       |
| 时钟偏差 | `last_sync_time` 回退 5 分钟作为安全边界，防止飞书侧与本机时钟不一致漏行  |
| 无新数据 | 直接返回，不写库、不调用任何 TokBrain 接口，空闲开销约等于一次 base 查询    |

**为什么不需要 D 路**：D 路的全部价值是把延迟从 60 秒压到 1 秒。既然接受分钟级，就没有必要为它引入飞书自动化配置、机器人群、事件总线常驻这三个外部依赖点——它们每一个都可能静默失效，而收益是省下不到一分钟。

⏸ **未来升级路径**：若日后需要秒级响应，按 4.2 表 D 路接入即可，A 路的代码不用改，两者共用 `record_id` 去重，天然可叠加。

## 5. 诉求三：Obsidian 与 TokBrain 并行

### 5.1 现状问题定位

`bridge_feishu_obsidian.py`：

```
:520-521   job = tb.ingest(work_ids); tb.wait_job(job["id"])   # 同步阻塞，最长 600s
:583-584   work_ids = process_link(...); export_to_obsidian(...)  # 处理完才导出
```

`main()` 是单线程 for 循环，一条记录从预检到导出全程占用，Obsidian 侧完全空等。

### 5.2 改造：拆成两条独立流水线

**快轨 A —— 收件即归档（目标 < 5 秒）**

```
新行(推或拉得到) → 规范化 aweme_id/URL
  → 计算笔记路径（此时就固定，后续只覆盖）
  → 写占位笔记（frontmatter 完整 + 正文为占位提示）
  → 记入本地队列 dispatch.json（status=queued）
  → 回写飞书状态列「待处理」（可选）
```

占位笔记示例：

```markdown
---
title: "一不小心发现求职skill"
source: douyin
url: https://v.douyin.com/xxxx/
aweme_id: "7673452209631491813"
feishu_record_id: recXXXXXXXX
tags: [教程, 求职]
topics: []
projects: []
status: processing
work_id: null
captured_at: 2026-08-29 02:00
tokbrain_synced_at: null
---

> ⏳ TokBrain 正在处理这条视频，转写、关键帧与总结完成后会自动回填到本笔记。
> 原文链接：<https://v.douyin.com/xxxx/>
```

**慢轨 B —— 处理完成后回填**

```
队列取出 queued 条目 → 创建 import batch → 等预检终态 → confirm → ingest
  → 轮询 job（终态：succeeded/failed/partial/cancelled）
  → 成功：obsidian/manifest 取正文 + 关键帧建立硬链接
  → 覆盖笔记正文、写入关键帧片段、status 迁移为 processed、填 work_id
  → 失败/需补件：写 status 与 error_code，正文保留占位提示
```

### 5.3 并行落地方式

按侵入性从低到高，三选一（建议从 1 起步）：

| 方案                  | 做法                     | 优点        | 代价           |
| ------------------- | ---------------------- | --------- | ------------ |
| 1. 双进程              | 快轨脚本常驻；慢轨脚本另起进程，共享队列文件 | 改动最小，可先跑通 | 需处理文件锁       |
| 2. 单进程 asyncio + 队列 | 一个常驻进程内两条协程，内存队列 + 落盘  | 无锁，状态一致   | 需重写 `main()` |
| 3. TokBrain 内置调度    | 在后端加 ingest 完成回调       | 最干净       | 要改后端代码与发布流程  |

队列文件建议：`data/pipeline/dispatch.json`（与 Vault 解耦，不污染笔记目录），用 SQLite 更好——`data/pipeline/dispatch.db`，天然支持并发与事务。

### 5.4 幂等与重试

| 规则   | 说明                                                     |
| ---- | ------------------------------------------------------ |
| 笔记路径 | 快轨固定为 `{VAULT_NOTES}/{首标签}/{aweme_id}-{标题}.md`，回填用同一路径 |
| 去重键  | `feishu_record_id` + `aweme_id`，任一命中即视为已处理             |

## 6. 诉求四：存储方案

### 6.1 设计原则：分层唯一权威

**每种数据只在一个地方存实体，其他位置一律用引用或硬链接。** 只有形态不同（向量索引 vs 文本笔记）才算必要冗余。

### 6.2 实测依据

```
os.link(r'D:\code\TokBrain-main\data\_hl_xxx.src', r'D:\ObsidianVault\_hl_xxx.dst')
→ 创建成功，st_ino 相同，st_nlink = 2，两份目录项只占 5 字节磁盘空间
```

两目录同在 D 盘同一 NTFS 卷，**硬链接可用**。

### 6.3 数据归属表

| 数据             | 唯一实体位置                         | Obsidian 侧                  | TokBrain 侧   | 额外占用          |
| -------------- | ------------------------------ | --------------------------- | ------------ | ------------- |
| 作品笔记（Markdown） | `D:\ObsidianVault\00收件箱\视频收藏\` | 实体                          | 不存           | 0             |
| 关键帧 JPG        | `data\keyframes\<aweme_id>\`   | **硬链接** 到 `99附件\keyframes\` | 实体           | **0**         |
| 图文资产 OCR 图     | `data\media\`                  | **硬链接**                     | 实体           | **0**         |
| 语义索引 / 知识块     | `data\douyin_rag.db`           | 不存                          | 实体（形态不同，非冗余） | —             |
| 总结文本           | 写入笔记正文                         | 实体                          | DB 存摘要用于检索   | 极小（KB 级，形态不同） |
| 源视频（远程）        | 处理完删除                          | 不存                          | 临时           | 0             |
| 源视频（本地补件/上传）   | `data\source-assets\`          | 不存                          | 实体，作品删除时清理   | 0             |

### 6.4 目录结构

```
D:\code\TokBrain-main\
├── data\
│   ├── douyin_rag.db            # 索引与元数据唯一权威
│   ├── keyframes\<aweme_id>\    # 关键帧唯一实体（只读）
│   ├── media\                   # 图文资产唯一实体
│   ├── source-assets\           # 本地源文件，作品删除时清理
│   └── pipeline\dispatch.db     # 新增：流水线队列与状态机
│
D:\ObsidianVault\
├── 00收件箱\视频收藏\<标签>\<aweme_id>-<标题>.md   # 笔记唯一实体
└── 99附件\
    ├── keyframes\               # 硬链接镜像（TokBrain 关键帧）
    └── media\                   # 硬链接镜像（TokBrain 图文资产）
```

硬链接镜像单独建 `keyframes/` / `media/` 子目录，与用户自有附件物理隔开，便于整体管理和排查。

### 6.5 硬链接的三条注意事项（重要）

1. **删除语义**：硬链接双方平权。TokBrain 删作品时若只删自己那份，Vault 里的图**仍在且笔记不碎**（这是好事），但磁盘空间不会释放，直到 Vault 侧链接也删掉。清理脚本必须**两侧同步删**，否则产生"幽灵占用"。
2. **备份工具**：多数备份/压缩工具会把两个硬链接当两个独立文件处理，导致备份体积翻倍。备份 Vault 或 `data/` 时要用支持硬链接去重的工具（WIM / tar / restic 等），不要直接用朴素 `Copy-Item` + 7z。
3. **跨盘失效**：硬链接不能跨卷。若将来把 Vault 移到其他盘符或移动硬盘，需自动降级为符号链接（`mklink /J`）或实体复制，脚本要能检测并处理。

### 6.6 被否决的替代方案

| 方案                             | 否决理由                                                |
| ------------------------------ | --------------------------------------------------- |
| 目录 junction（`mklink /J`）       | Obsidian 对 junction 内文件的索引行为不稳定，且部分同步插件会跟随或跳过，行为不一致 |
| 笔记里写绝对路径 `![](file:///D:/...)` | 能显示但不进 Obsidian 图谱、搜索与双链，失去知识库价值                    |
| 直接引用 `data/keyframes` 原路径      | 同上，且把 Vault 与后端目录强耦合，目录一改笔记全碎                       |

## 9. 风险与红线复述

1. **不得绕过下载权限**：`download_permission = denied` 时不得用第三方下载器强下，作品停在 `needs_supplement` 等人工补件。
2. **不暴露到公网**：变更感知全程走飞书长连接出站，本机不开任何入站端口。
3. **后端运行环境**：TokBrain 后端仍须双击 `启动.cmd` 启动，避免 safe-delete shim 中断视频处理。
4. **备份一致性**：数据库与资产目录须同一时间点备份；启用硬链接后要换用支持去重的备份工具。
