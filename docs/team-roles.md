## 1. 三角色定义

### A — 统筹与校验（Coordinator & Verifier）
- 需求拆解、排期、跨角色协调，维护责任矩阵与进度看板。
- 把关交付物是否符合 `pipeline-v2-plan.md` 的**接口契约、EARS 需求与红线约束**。
- **合并/验收门禁**：每个 P 完成后由 A 出具验收结论，未过不进下一环。
- 升级决策：遇到合规/红线/跨域依赖问题，直接上报用户（北辰之渊）。

### B — 开发（Developer）
- **串行实现 P3 → P4 → P5**（执行模型见第 4 节）。
- 复用已建基础：`dispatch.db` 队列、双轨（占位/回填）、NTFS 硬链接、`ensure_columns()`。
- 每个 P 配套单元测试，自测通过后再交 C。
- 不触碰红线：不得自动抓取抖音收藏夹、不得公网暴露 Webhook。

### C — 测试（Tester）
- 针对 P3/P4/P5 产出并执行测试用例（见 `docs/test-cases-p3-p5.md`）。
- 覆盖正常流、边界、异常、幂等、并发、回归。
- 输出验收清单与上线风险清单，把关是否阻断上线。

## 2. P3/P4/P5 责任矩阵

| 工作项 | 内容 | B（开发） | C（测试） | A（统筹校验） | 依赖 |
|---|---|---|---|---|---|
| **P3** | 状态回写飞书 + 失败重试/人工重投 | 实现 | 用例 + 执行 | 验收 + 拉设计师确认交互 | P1、P2 |
| **P4** | 入站 API `/inbox/items` + 适配器插槽 | 实现 | 用例 + 执行 | 验收接口契约 | 无（P0–P2 已完，可并行开发） |
| **P5** | 用户触发式导出工具（书签小工具） | 实现 | 用例 + 执行 | 验收合规（不自动抓取） | P4 |

---

## 3. 每个 P 的交付物与门禁

B 交付：代码 + 单元测试 + 自测记录。
C 交付：`test-cases-p3-p5.md` 中对应用例的执行记录（签署通过/阻塞）。
A 交付：验收结论（通过 / 打回 + 理由）。

三份齐全，该 P 才算关闭，方可启动下一个 P。

---

## 4. 执行模型（用户已确认）

**B 串行开发（P3 → P4 → P5），C 全程跟进每步测试，A 每环校验。**
非多代理同时改同一仓库，冲突最小、可回溯；不追求同一时刻多代理并行写码。

- 启动顺序：P3（依赖 P1/P2 已落地）→ P4（纯新增，可与 P3 收尾重叠准备）→ P5（依赖 P4 接口）。
- 节奏：B 完成一个 P → C 跑该 P 用例 → A 验收 → 进入下一个 P。

---

## 5. 红线提醒（全员）

1. **不实现抖音收藏夹自动抓取**（README「固定安全边界」明令禁止账号/收藏夹扫描与自动登录）。
2. **不公网暴露 Webhook**（仅监听 127.0.0.1，违反则否决）。
3. 入站数据必须随 `rights_attested` 权利声明提交（P4 强制）。
4. P5 导出工具须通过静态合规断言：不翻页、不持登录态、不模拟请求、不后台常驻。

---

## 6. 角色实例化说明

本登记为**角色定义**，非运行中的子代理。后续执行时，可按需在会话中实例化：
- B/C 以子代理（后台）形式派活，携带本文件与对应 P 的接口契约作为上下文；
- A 由主会话承担统筹与验收，不另起子代理，避免协调视图分裂。

> 注：当前项目仅 1 名成员（北辰之渊，owner）。设计师与测试为外部补充角色，P3 的交互入口需设计师参与，C 的测试执行需测试同学介入——已在 P3 事项中注明。
