## 执行顺序（不要一次投 6 条）

### 第 0 步：确认服务与通道

```
tb_status(include_sync=true)
```

- 后端没跑 → 先 `tb_service_start`，等就绪再继续
- 桥没跑 → `tb_sync_start(download=false)`（补元数据不需要下载视频）
- 桥在跑 → 继续

**通道自检**：先投第 3 条（`recvtQIraSbs5I`），它刚被实测能解析。如果它报
`browser_unavailable`，说明后端不是 browser 通道，**立刻停**，回话给老张，
不要改环境变量自己折腾。

### 第 1 步：先只投 1 条

```
tb_sync_replay(record_ids=["recvtQIraSbs5I"])
tb_sync_wait(timeout=120)
```

选第 3 条是因为它刚做过端到端验证，是当前最确定的一条——用确定性最高的一条
确认链路，而不是拿不确定的条目试错。

- `tb_sync_wait` 返回还在跑 → **再调一次 `tb_sync_wait`**，不要重新导入
- 有 `awaiting_confirm` → 先 `tb_sync_pending` 看一眼，再 `tb_sync_confirm`
- **浏览器解析要 10–15 秒**，比过去慢，一次 wait 不够是正常的，不是卡死

### 第 2 步：看第 1 条的结果决定走向

| 结果 | 动作 |
|------|------|
| 拿到标题/作者，状态 processed | 继续第 3 步 |
| `browser_unavailable` | **停**。这是本机工具/开关问题，不是风控。回话给老张，不要重试，不要改配置 |
| `access_forbidden` / `risk_verification` | **停**。抖音这次真的拦了，说明有新的风控。立刻结束本轮，不要换链接再试 |
| `network_timeout` | 等 30 秒再试一次；连续两次就停，报告网络问题 |
| 429 | 等 60 秒再试一次；连续两次 429 就停，报告本地限流未恢复 |
| 作品不存在/已删除（`work_unavailable`） | 这条跳过，记为「链接已失效，无法补齐」，继续投下一条 |

### 第 3 步：逐条投剩下的，每条之间等

```
tb_sync_replay(record_ids=["recvtNjaMTzIPA"])
tb_sync_wait(timeout=120)
```

**一条一投、一条一等**，不要一次传多个 record_id——本地限流就是被批量打出来的。

顺序建议：第 3 条（验证）→ 第 2 条 → 第 4 条 → 第 5 条 → 第 6 条 → 第 1 条。
