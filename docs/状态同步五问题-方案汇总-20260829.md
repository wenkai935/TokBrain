## 三、问题 1 补充说明（LID 生成时机）

- **批量抓取落表**：doubaosave `build_record` 在链接兜底后调用 `make_lid(链接)` 生成 `LID` 写入记录 → 每批 200 条批量创建。**落表即生成**。
- **手机直发落表**：飞书行只有「链接」列（无 LID）→ bridge 快轨读取时 `_row_tuple` 取 LID，为空则 `_make_lid(link)` 生成，并：①回填飞书 LID 列 ②写入 dispatch.lid ③写入 Obsidian frontmatter `lid`。
- **存量兜底**：bridge 启动时 `Feishu.backfill_lids()` 对「链接有值、LID 为空」的历史行补生成（幂等）。
- 两入口规则一致（`lid_` + sha256(链接) 前 16 位），同一链接 LID 全局唯一。

## 四、问题 2 补充说明（双轨唤起机制）

- 唤起方式 = **bridge 常驻轮询 + SQLite dispatch 队列**：
  1. `python bridge_feishu_obsidian.py --watch` 启动后每 `POLL_CYCLE`(60s) 执行一轮 `run_once`。
  2. **快轨**（收件即归档，秒级）：`get_updated_rows` 按「最后修改时间」增量拉飞书新行 → `write_placeholder_note` 立即写 Obsidian 占位笔记 → `store.enqueue` 入队列。
  3. **慢轨**（深度处理，分钟级）：`process_queue` 消费队列 → TokBrain `import_link`/`ingest` → 完成后 `backfill_note` 回填 Obsidian + 回写飞书状态。
  4. 去重与断点：`last_modified_cursor` + `synced_record_ids` 双保险；游标带 CURSOR_SKEW_SECONDS 安全回退。
- 待实施项：可选把 `POLL_CYCLE` 调至 30s；飞书 webhook 因用户身份订阅受限暂不做。

## 五、问题 4 补充说明（v2：LID 贯通 works，已实施）

- 后端改动（已实施）：
  1. **模型**：`app/models.py class Work` 加 `lid: Mapped[str | None] = mapped_column(String(24), index=True)`。
  2. **迁移**：`app/services/migrations.py` 新增 `migrate_to_v10`（works 缺 lid → 幂等 ALTER + `ix_works_lid` 索引），`SCHEMA_VERSION` 9→10，`prepare_database` 注册；真实库已执行。
  3. **生成工具**：`app/services/f2_links.py::make_lid`（与 bridge/doubaosave 同规则，已三端验证一致）。
  4. **创建写 lid**：`app/services/import_queue.py::_confirm_import_items` 建 Work 时 `lid=make_lid(item.input_url or "")`。
  5. **LID 去重**（核心）：`_confirm_import_items` 中 platform_work_id 未命中时按 `make_lid(item.input_url)` 查 `Work.lid` 复用；`_process_item_inner` resolve 后同样兜底。**避免 work_id 写入空值/失败时重复建 work**。
  6. **接口暴露**：batch_view items 增加 `lid`；`app/routers_v2/library.py::works` 支持 `?lid=` 过滤。
- bridge 侧：work_id 保留（成功路径写 dispatch.work_id）；待补件/失败时 work_id 为空由 LID 兜底。
- 回写主键：飞书回写仍用 `record_id` 定位行；**LID 作为 works ↔ dispatch ↔ Obsidian ↔ 飞书行的跨系统关联主键**。

## 六、问题 5 补充说明（v2：自动回扫，已实施）

- 新增 `rescan_supplements(tb, store)`（bridge_feishu_obsidian.py），接入 `run_once`（process_queue 之后、writeback 之前）：
  1. 取 `status='needs_supplement'` 行；
  2. 定位作品优先级：`dispatch.work_id` → `_work_id_for_lid(dispatch.lid)`（works.lid 同源飞书 LID）→ `_work_id_by_source_url(dispatch.link)`；
  3. 直读 works 表 `processing_state`，== `processed` 则 `backfill_note` + `store.update(rid, status="processed")` + `mark_note_status`；
  4. 下一轮 `writeback_feishu_status` 自动回写飞书「已归档」。
- 触发器 = **watch 轮询每轮自动回扫**；`--retry` 保留作手动兜底。

## 七、v1 vs v2 对比（问题 4/5）

| 维度 | v1（仅 bridge） | v2（本方案，LID 贯通 works） |
|---|---|---|
| 改动面 | 仅 bridge（NeedsSupplement 带 work_ids + rescan 按 work_id） | bridge + 后端（models/迁移/写入/去重/by-lid 查询） |
| work_id 空值/失败 | 无法定位作品 | **LID 兜底可定位**（works.lid 同源飞书 LID） |
| 去重能力 | 仅 platform_work_id | **+ LID 层去重**（同原始分享链可识别，避免重复建 work） |
| 一致性 | LID 仅飞书侧，works 无对应 | **works.lid 与飞书 LID 同源**，三端可对账 |
| 回写可靠性 | 依赖 work_id 链路 | 以 LID 为主键索引，work_id 仅作加速 |
| 缺点/风险 | 改动小但定位脆弱、补件失败难恢复 | 后端改动面大；依赖 input_url 与飞书链接同串；历史旧 work 无 lid 需按 source_url 重算或留空；需幂等迁移 |
