## 二、真正根因：Hermes 的 tool_search 延迟加载

关键日志：`5 core/visible tools kept, 31 deferred (~5724 tokens), listing full (budget ~4000)`

Hermes 有 **tool_search 桥接机制**（`tools/tool_search.py`）：
- 36 个工具里只让 **5 个常驻可见**（`kb_search` 在常驻里——所以模型每次都用它）；
- 其余 **31 个进延迟池**，包括 **tokbrain 的全部 5 个工具**；
- 模型要用延迟工具，得**先主动调 `tool_search` 按名字搜索**，再 `tool_describe` 加载 schema，才能调用。

判定逻辑（`tool_search.py:149-161`）：
```python
if name in _core_tool_names(): return False   # core 工具常驻
toolset = _registry_toolset(name)
return toolset is not None and (
    toolset.startswith("mcp-") or ...)        # MCP 工具一律延迟，无法配成常驻
```
**所有 MCP 工具天然被延迟**，配置 `defer: []` 也救不了（那只管内置工具）。

### 为什么模型不知道要搜

延迟池的**名字清单**嵌在 `tool_search` 桥的描述里。日志显示：
```
deferred 需要 ~5724 tokens, 但 listing budget 只有 4000
```
**清单被截断了**——tokbrain 工具名大概率没进模型可见的目录。所以模型压根不知道有个 `tokbrain_search`，自然不会去搜，只会用它看得见的 `kb_search`。

一句话：**不是"选错工具"，是"根本没看见这个工具"。**

## 三、修复方案（三选一，给对比）

| 方案 | 做法 | 有效性 | 风险/代价 | 推荐 |
|---|---|---|---|---|
| A. 提 listing 预算 | `config.yaml` 加 `tools.tool_search.listing_max_tokens: 8000`（实际需 5724），让完整清单进上下文 | 高——模型能看见 tokbrain 名字 | 低，一处配置、可逆；多耗 ~1.7K tokens/轮 | ⭐ **先试这个** |
| B. 加 SOUL 路由规则 | 写"知识问题先 tool_search 搜 tokbrain" | 中——依赖模型遵守 | 又造规则源；且若名字没进清单，搜也可能不中 | 备选，A 不够再叠加 |
| C. 改 Hermes 内核把 MCP 工具设常驻 | 改 `toolsets.py` 的 `_HERMES_CORE_TOOLS` | 最高 | **动闭源平台代码，升级会被覆盖，风险高** | ❌ 不做 |

**推荐 A**：它对症（清单被预算截断），改动最小、可逆、在配置层不动内核。

### A 的具体改动（本地产出，未同步）

在 `/vol1/1000/hermes-state/config.yaml` 增加：
```yaml
tools:
  tool_search:
    listing_max_tokens: 8000
```
注：当前 config.yaml **没有** `tools.tool_search` 段，走的是默认值 4000。新增这段只覆盖预算，其余保持默认。
