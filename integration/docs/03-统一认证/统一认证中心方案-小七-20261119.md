# 小七：设备间访问安全与统一认证中心方案

调研日期：2026-11-19  
范围：本地代码（源码仓库 + NAS 实际部署拷贝）+ GitHub + MCP 官方规范 2026-07-28 + 业界资料

---

## 一句话结论

**别照搬网上的 MCP OAuth。** 你的 MCP 全是 stdio 本地子进程，官方规范明确说这种情况不该走 OAuth。你真正缺的是**服务间认证（谁在调用谁、能调什么、留不留痕）**，用一套轻量的"凭据中心 + scope 分级 + 审计"就能解决，不需要浏览器授权、不需要网关集群。

---

## 1. 先纠正一个关键认知

网上大军宣传的 "MCP Authorization = OAuth 2.1 + PKCE + CIMD + DCR"，针对的是**远程 MCP server + 第三方客户端 + 多租户**。我核对了官方规范原文（modelcontextprotocol.io，2026-07-28）：

> Authorization is **OPTIONAL**. Implementations using an HTTP-based transport **SHOULD** conform to this specification. Implementations using an **STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment**.

你的 4 个 MCP（`home_rules`/`home_history`/`xiaoqi_music`/`tv_control`）在 `config.yaml` 里全是：

```yaml
command: /opt/hermes/.venv/bin/python
args: ["-m", "home_rules.server"]
```

即 Hermes 拉起的本地子进程、stdio 通信。所以：

- 规范里那套 401 → 发现授权服务器 → PKCE → 换 token 的流程，**你已经"合规地"跳过了**（凭据从环境变量进，正是规范给 stdio 指的路）。
- 你担心的不是"客户端授权"，而是**服务之间互认身份 + 权限收口**——这是 OAuth 2.0 里另一个 grant（client credentials / 机器对机器），跟"MCP Authorization"不是一回事。

## 2. 现状盘点与安全缺口

| 访问路径                 | 当前凭据                                                       | 问题                                                             |
| -------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| 语音 → 桥接 → 小智         | `.config.yaml` `auth.enabled: false`，`allowed_devices: []` | 任何能连上 `ws://192.168.10.104:8000` 的都可伪装成音箱；无设备身份                |
| Hermes → 小智          | `API_SERVER_KEY`（环境变量）                                     | 静态长期密钥，全系统共用，泄露无感、无法单独吊销                                       |
| MCP → Home Assistant | `HASS_TOKEN` 注入到 3 个 server                                | 静态长期 token，且是**全能 token**，无 scope 分级；明文落在 docker-compose/.env  |
| MCP → 电视助手           | `TV_HELPER_TOKEN`                                          | 同上，静态                                                          |
| MCP → 音乐桥接           | `MUSIC_URL=http://host.docker.internal:4400`，**无 token**   | 裸 HTTP，局域网内任何设备都能点歌/控制播放                                       |
| MCP → 天气等插件          | `xiaozhi/data/.config.yaml` 里明文 `api_key`                  | 见下方"立即止血"                                                      |
| 语音入口是否认人             | `hermes_voice.py` 明确"说话者身份未认证"                             | 这是**设计选择**，靠 fail-closed 证据校验 + 高风险设备硬边界缓解；不是缺陷，但要在认证中心方案里明确边界 |

**三个结构性问题**：

1. **静态长期凭据散落**：每个服务各拿各的 token，明文分布多处，无集中轮换、无单项吊销。
2. **无权限分级**：一个 token 往往是全权限，服务被攻破 = 整个家被控制。
3. **无审计**：谁在何时开了哪盏灯、哪种设备发起的调用，没有统一记录，事后无法追溯。

### 立即止血（与认证中心无关，但必须先做）

- `xiaozhi/data/.config.yaml:69` 有一串 **32 位和风天气 `api_key`（`a861d0d5…`）是真实值**，明文存盘。建议**轮换该 key**，并移出仓库到环境变量/secret 文件；同文件的 HA key、ragflow、metaso 目前是 `xxx` 占位符，不算泄露。
- 该 `.config.yaml` 应加入 `.gitignore`，避免随备份/同步扩散。
- 音乐桥接先加一个共享密钥（哪怕是静态的），堵住裸 HTTP。

## 3. 方案对比

| 方案                                          | 解决什么                   | 代价                                                               | 对你的判断                                  |
| ------------------------------------------- | ---------------------- | ---------------------------------------------------------------- | -------------------------------------- |
| **A. 完整 MCP OAuth 2.1**（规范那套 PKCE/CIMD/DCR） | 远程 MCP、第三方客户端、多租户授权    | 浏览器授权环节对**无屏音箱不成立**；4 个 stdio server 规范明确不适用                     | ❌ 不推荐，方向就错了                            |
| **B. MCP Gateway**（集中网关 + token exchange）   | 大量 MCP server、多用户、统一审计 | 你的 MCP 是本地 stdio，加网关多一跳多一个故障点；企业级组件（Kong/Solo/TrueFoundry）对单家庭过重 | ⚠️ 过度设计                                |
| **C. 全套 IdP**（Keycloak / Authentik）         | 多服务 + 真人用户 + SSO       | Keycloak 是 Java 重型；单家庭只有你一个人"用户"                                 | ⚠️ 可选，非首选；真要上选 Authentik（比 Keycloak 轻） |
| **D. 自建轻量凭据中心 + 短期 token + scope + 审计**     | 服务间互认、权限收口、可吊销、可追溯     | 一个几百行的小服务 + 各 server 加一层校验                                       | ✅ **推荐**                               |
| **E. 双向 TLS（mTLS，自建小 CA）**                  | 跨网段/不可信网络下的设备强认证       | 要管证书签发与轮换                                                        | ✅ 进阶，阶段 2 再上                           |

## 4. 推荐方案：分三阶段落地

### 阶段 0 — 止血（本周，零架构改动）

1. 轮换并外置泄露的天气 key；`.config.yaml` 入 `.gitignore`。
2. 音乐桥接加共享密钥；HA 给小七建**独立、最小权限**的 token（只授权它实际控制的实体），不要复用全能 token。
3. 清点所有静态密钥，列一张"密钥-用途-持有人-轮换日期"清单——这是认证中心的输入。

### 阶段 1 — 统一认证中心（核心，自建轻量服务 `xiaoqi-auth`）

跑在 NAS 的一个容器，只做三件事：

| 能力            | 说明                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| **服务注册表**     | 每个调用方一个 `client_id` + 允许的 `scope` + 允许访问的资源。`home_rules` 只能写 HA 的灯/插座；`home_history` 只能读；`xiaoqi_music` 只能访问音乐桥接 |
| **短期凭据签发**    | 用 client credentials 换 5–15 分钟有效的 JWT，声明 `aud`（目标资源）、`scope`、`cid`、`exp`；启动时换取、过期续期                              |
| **JWKS + 审计** | 暴露 JWKS 端点供下游验签；每次调用记一条审计：`时间/调用方/目标/动作/结果`                                                                      |

下游改造（改动很小）：

- **音乐桥接、电视 helper**：加一层薄校验，验 JWT 的 `aud`/`scope`/`exp`（几十行中间件）。
- **Home Assistant**：它自己的 token 机制要保留。做法是让 `xiaoqi-auth` 做**反向代理**——校验通过才把 HA token 带上转发，业务 server 不再持有 HA token。
- **不碰语音"认人"**：语音入口继续保持 fail-closed 证据校验 + 高风险设备硬边界。认证中心只管"机器身份"，不假装能认出说话的人。

### 阶段 2 — 进阶（按需）

- 服务跨网段、或走不可信网络时，上 **mTLS**（自建小 CA，每服务一证），或引入 **Authentik** 做正式 IdP。
- 把审计日志接进你现有的检查链路，做异常告警（如某服务半夜调门锁）。

## 5. 落地顺序与最小 diff

```
阶段0（止血）  →  阶段1（凭据中心 + scope + 审计）  →  阶段2（mTLS/Authentik，按需）
  本周              2–3 周，可分服务灰度                 仅跨网段才需要
```

**最小可跑闭环**：先给音乐桥接这一条路径做完整示范（现在它最裸）——`xiaoqi-auth` 签发 → 桥接校验 → 审计落盘；跑通后再照模板接到 HA、TV。这样每一步都能验证，不会一次性大改。

**不要做的事**：不要为了"统一认证"去引入浏览器登录页（音箱没屏幕）、不要把用户密码塞进 MCP（你只有一个真人用户）、不要一上来就上 Keycloak/Gateway 集群。

## 6. 调研来源

**官方规范**：MCP Authorization 2026-07-28（modelcontextprotocol.io / modelcontextprotocol.com.cn）；确认 stdio 走环境变量、token audience 绑定（RFC 8707）、禁止 token passthrough（防 confused deputy）。

**业界资料**：MCP OAuth 流程（Scalekit、Casdoor、AfterGradient）；网关与 EMA 企业托管授权（AgentReady、ChatForest、Akto、cybertizeweb）。关键数据：仅约 8.5% 的 MCP server 实现了 OAuth 2.1，53% 把凭据硬编码在配置里——你的情况属于后者，是普遍问题而非个例。

**GitHub 参考实现**（都偏企业级/新项目，星数很低，仅供读思路，不建议直接依赖）：

- `glincker/theauth-go` — 自托管 Go 认证库，含 MCP 授权（RFC 9728）、DPoP、RBAC，MIT
- `TevBenji/OAuth-2.1-MCP-Gateway` — 自托管 OAuth 2.1 服务 + 反向代理，audience-scoped JWT
- `xianhong1208/MCP_Gate` — Python/FastMCP，签发 token 供 MCP server 校验
- `RedFox-Soft/OAuth-server.ts` — Bun/TS，带管理控制台

**本地代码**：`deploy/hermes/profile/config.yaml`（MCP 挂载方式）、`mcp/*/server.py`（各 server 实现）、`voice-patch/hermes_voice.py`（受限语音入口）、`xiaozhi/data/.config.yaml`（明文密钥）。

## Verdict

你的直觉对——设备间访问确实没有统一的安全边界。但解法不是网上热炒的 MCP OAuth，而是**服务间认证**：先止血（轮换明文 key、堵裸 HTTP），再上一个轻量 `xiaoqi-auth` 做集中签发 + scope 分级 + 审计，最后按需加 mTLS。语音"认人"保持现状即可，那是设计选择不是漏洞。
