# 小七（Open-XiaoAI）代码审计报告

审计方式：静态阅读（不运行系统、不跑测试）。按 ponytail-audit 规程，只读、不改任何代码。
审计日期：2026-11-19

## What this repo does（这个仓库做什么）

把小爱音箱或普通蓝牙音箱改造成家庭 AI 语音管家：语音经桥接传给小智服务端做识别，再交给 Hermes Agent 理解意图、调用工具，通过 Home Assistant 控制米家/海尔/电视等**真实物理设备**，也能离线放歌和主动播报。主体在 `open-xiaoai-main`（Python 后端/桥接/终端 + Rust 客户端 + MCP 服务），另有 `xiaoqi/`、`xiaozhi/` 是运行时数据，`promo-video*` 是宣传视频脚本。

**负载假设**：单个家庭，2–5 个语音终端同时在线，16 台设备、300+ 可控项，7×24 长期运行。这不是高并发 Web 服务——所以"错一次"的代价不是请求失败，而是**真实设备被误开关**或**长期运行后假死/崩溃**。所有判断按这个负载来。

## Must fix（必须修：错误、安全、数据丢失、在预期负载下崩溃）

### 1. 高风险设备分级能被绕过，燃气/热水器可能被写进联动
- **位置**：`deploy/hermes/profile/mcp/home_rules/rules.py:35-68, 229-231`
- **是什么**：这是唯一的硬代码安全边界，决定哪些设备禁止放进自动联动。它靠中文名关键词（"燃气/热水器/取暖"等）和 domain 白名单判断。
- **问题**：一台 domain 是 `switch`、名字叫"厨房即热"的燃气热水器，既不在 high domain 里，名字也不含关键词，就被判为 `low`，校验放行，保存逻辑真的把控制它的自动化写进 HA。提示词只是软建议，模型本就不可靠，这里是最后一道防线。
- **修复**：分级不要靠名字猜。在配置里显式标注设备风险（给高风险实体加名单/标签），未知设备默认按 `high` 处理、人工降级。
- **不修的后果**：设备名不含关键词时，可能建出自动开关燃气/取暖的联动，无人确认就执行。

### 2. 场景已经执行了，却告诉用户"没执行"
- **位置**：`deploy/hermes/profile/mcp/home_rules/scene_run.py:216-231`、`server.py:289-298`
- **是什么**："我回来了"这类场景，先让 HA 触发脚本，再轮询设备状态确认。
- **问题**：`script.turn_on` 成功后，若轮询时 `ha.state()` 因 HA 抖动抛异常，同一个 try 把它当成整体失败，于是播报"'我回来了'没有执行"。但灯其实已经开了。
- **修复**：把"触发"和"验证"拆成两个 try；触发成功后即使验证失败，也回答"已触发，但没能确认状态"，而不是"没有执行"。
- **不修的后果**：物理设备已动作却报告没动作，用户重复下达口令，可能二次误操作。

### 3. 一行畸形日志就能让整个 Rust 客户端进程退出
- **位置**：`packages/client-rust/src/services/monitor/kws.rs:51-53`、`services/monitor/file.rs:39-41/67/71/92`、`Cargo.toml:10`
- **是什么**：客户端盯 `kws.log`，每行按 `@` 拆分，取第一段 `parse` 成数字。
- **问题**：日志被写坏一行、或轮转时读到半行，`data[0].parse::<u64>().unwrap()` 直接 panic；`file.rs` 每 10ms 读 `metadata().unwrap()`，轮转删除瞬间也会 panic。release profile 是 `panic="abort"`，tokio 的任务隔离失效——任何一处 panic 都终止整个进程，麦克风、播放、WebSocket 一起死，且无自动拉起。
- **修复**：这几处 `unwrap` 改成 `match`/`if let`，畸形行跳过并记告警；热路径上不能 panic。
- **不修的后果**：一次日志轮转就可能让音箱端整体掉线，直到人工重启。

### 4. 红外开机等 45 秒，但实测要 75 秒——重试会把刚开的电视关掉
- **位置**：`deploy/hermes/profile/mcp/tv_control/tv.py:31, 143-164`
- **是什么**：电视待机时网络断开，开机只能靠小爱红外，而这个红外码是开关切换（toggle）——发第二次就关。
- **问题**：`ensure_on` 发一次红外后只等 `IR_WAKE_S=45` 秒，而代码自己的注释写明实测电视要 15–75 秒才联网。若电视在 45–75 秒之间回来，45 秒时抛错，模型/用户重试 → 电视还在启动、网络未通 → 又发一次 toggle → 把正在启动的电视关掉。
- **修复**：把等待上限提到大于观测值（至少 90 秒）并在等待中用 helper 状态确认；重试路径加幂等保护——距上次发红外不足 X 秒不许再发。
- **不修的后果**：用户说"打开电视"，结果电视被关掉，正是 README 承诺"不会弄反"要避免的场景。

### 5. 保存联动是"先读后写"且没有跨进程锁，并发下产生重复规则或覆盖
- **位置**：`deploy/hermes/profile/mcp/home_rules/server.py:127-168`、`pending.py:23-59`
- **是什么**：保存时先读现有规则、判断是否重复、再写 HA 配置；待确认项存在一个共享 JSON 文件里。
- **问题**：2–5 个终端并发保存同名规则时，两边都读到"不存在"，各自生成不同 id 写入 → 两条同名规则，之后 `find` 返回多项，`run`/`delete` 都报"有多个匹配"，这条规则再也定位不到。`Pending` 用的是 `threading.Lock`，只锁单进程；文件注释明说"every Hermes process sees the same list"，多进程同时 `record` 会各写各的、后写覆盖先写，用户确认时漏保存。
- **修复**：`Pending` 改用文件锁（flock/fcntl），把 `_load→改→_store` 包进去；保存路径按固定 id 写，交给 HA 做幂等。
- **不修的后果**：多终端并发下规则静默丢失或重复，且之后无法单一定位删除。

### 6. WebSocket 发送没有超时，半开连接会让小七永久失联
- **位置**：`examples/xiaozhi/xiaozhi/services/protocols/websocket_protocol.py:135-150, 221-245`
- **是什么**：心跳和音频都走 `websocket.send()`，判活只看 `connected` 标志。
- **问题**：当 TCP 连接还在、但服务端/WiFi 已不读数据（服务端假死、WiFi 半开、对端接收窗口为 0）时，`send` 在发送缓冲填满后无限阻塞；心跳卡住，`connected` 仍是 True，重连分支永远不进。README 承诺"断网 30 秒，恢复后 1 秒内连回"，这种半开状态下做不到。
- **修复**：给 `send` 加 `asyncio.wait_for` 超时；超时就当断开，走 `_close_websocket` 重连。
- **不修的后果**：网络半开时设备看似在线实则永久失聪，无自动恢复。

### 7. 蓝牙音箱一断，语音终端的对话任务永久卡死
- **位置**：`examples/voice-terminal/voice_terminal/audio.py:370-376`、`terminal.py:295`
- **是什么**：`drained()` 等播放缓冲清空才让对话进入下一轮，而 `buffered` 只在音频回调 `pull()` 里递减。
- **问题**：蓝牙断开或设备停摆时回调不再执行，`buffered` 停在 >0，`drained()` 的 while 循环没有超时、永不退出；对话任务永久挂起，不再响应唤醒。健康检查只看麦克风 `stalled`（`terminal.py:295`），不检查扬声器，自动恢复绕过这个故障点。
- **修复**：`drained()` 加超时；超时按"播放失败"处理并重置缓冲，让状态机回到 WAKE。
- **不修的后果**：电脑语音终端遇到蓝牙断开就彻底哑掉，只能重启进程。

### 8. 判断电视开关机只看 adb 端口，不看真正的控制通道
- **位置**：`deploy/hermes/profile/mcp/tv_control/tv.py:104-115, 128-133, 143-164`
- **是什么**：`reachable()` 只探测 adb 的 5555 端口，用它决定电视开关；真正的控制走电视助手 HTTP 8765 + token。
- **问题**：电视开着、助手正常，但 adb 因调试被关或端口变更不可达时，`status()` 返回 None、`reachable()` 返回 False → `ensure_on` 判定电视关机 → 发红外 toggle → 把开着的电视关掉。和 #4 同属"误关设备"，但根因不同（判据用错通道），修 #4 修不掉这个。
- **修复**：判活改用 helper 的 `/status` 或 HA 电源状态；发红外前做二次确认。
- **不修的后果**：adb 端口独立失效时，开着的电视会被误关。

## Should fix（应该修：有风险但无测试、真实慢、重复、该删的代码）

### 9. 音频初始化失败后静默失效，程序"看起来在跑"但没声音
- **位置**：`examples/xiaozhi/xiaozhi/xiaozhi.py:158-167, 388-393, 401-406`
- `AudioCodec()` 失败只 `alert` 一下，CLI 部署下 `alert` 是空实现，`audio_codec` 保持 None；之后仍启动触发器线程，线程立刻 `AttributeError` 死亡，`set_device_state` 也在 `stop_streams()` 抛错。KWS/VAD/GUI 线程都活着，进程看似在线，音频却彻底失效，健康日志也没有。
- **修复**：初始化失败就 fail-fast 退出并写健康事件，不要带着 None 继续跑。

### 10. 服务端"连上就立刻断开"时没有退避，形成重连风暴
- **位置**：`examples/voice-terminal/voice_terminal/terminal.py:360-388`
- 退避只在 `connect()` 抛异常时生效；一旦握手成功就把 `delay` 重置为 1.0，而 `conn.closed.wait()` 返回后直接进下一轮、没有 sleep。服务端接受连接又立刻关闭时（后端反复重启、会话策略拒绝），变成高速空转，CPU/句柄抖动、日志暴涨。
- **修复**：把断开也计入退避；`closed` 返回后 sleep 当前 delay。

### 11. 批量删除逐个写且没有事务，中途失败就丢掉"已经删了哪些"
- **位置**：`deploy/hermes/profile/mcp/home_rules/server.py:263-273`
- "删掉 A、B、C"循环调用 `delete_config`，A、B 删成功后 C 抛 `HAError`，外层只返回"HA 出错"，已删信息全丢；用户重试又对 A、B 报"没有找到"。对比 `home_rule_confirm` 明确区分 saved 和失败项，这里没做。
- **修复**：像 confirm 一样返回 `deleted` 列表 + `problems`，逐个 try。

### 12. 多日统计里"每天亮灯时长"和"总时长"互相矛盾
- **位置**：`deploy/hermes/profile/mcp/home_history/history.py:195-211, 249-276`
- `_on_periods` 跳过离线时段算 `on_seconds`，`_per_day` 却按时间跨度重算。某天灯开着时设备离线 1 小时，`on_total` 报 3 小时，`per_day` 那天报 4 小时。提示词要求模型照数字念，于是同时播报"本周共 3 小时""周三 4 小时"。现有测试没覆盖"离线 + 多日"组合。
- **修复**：`_per_day` 用已算好的 `on_seconds` 按天切分，不要用跨度重减。

### 13. RPC 先发请求后登记接收端，快速响应会被丢掉
- **位置**：`packages/client-rust/src/services/connect/rpc.rs:109-126`
- `call_remote` 先 `send_request().await`，再往 pending 表插 oneshot。低延迟 LAN 里对端瞬时回复时，响应可能在 insert 之前到达 `on_response`，查不到条目被丢弃，调用方只能等满 10 秒超时。无并发测试覆盖。
- **修复**：先 insert pending 再 send_request。

### 14. 打断时注入的语音缓冲会覆盖残留音频，截断唤醒词后的话
- **位置**：`examples/xiaozhi/xiaozhi/services/audio/codec.py:67-91`
- barge-in 时 `temp_frames = speech_frames` 直接赋值覆盖；若 `temp_frames` 里还有上次不足一帧的残留 PCM（约 60ms），这些字节被丢弃，用户紧跟唤醒词说的话开头被截掉，和精心设计的 lookback 补偿相互抵消。
- **修复**：改成追加（`speech_frames` + 残留），不要覆盖。

### 15. 嵌入式上每 10 毫秒 fork 一个 shell 查播放状态
- **位置**：`packages/client-rust/src/services/monitor/playing.rs:52-75`
- 监控循环每轮跑 `run_shell("mphelper mute_stat")`（即 `/bin/sh -c`），再 sleep 10ms——约每秒 100 次、每天 860 万次创建两个进程，是 ARM 小音箱热路径上最贵的操作。且 `run_shell` 失败时 `start_monitor` 返回 Err，被 `let _ =` 吞掉，监控永久停止无告警。
- **修复**：降低频率（如 200ms）或走更轻的状态读取；失败时重试而不是退出循环。

### 16. 播放队列满时会阻塞消息接收循环，连接假死
- **位置**：`packages/client-rust/src/services/audio/play.rs:91, 120-126`、`connect/message.rs:339-354`
- `play()` 在消息 reader 循环里被直接 await，队列满时 `sender.send().await` 阻塞。aplay 写入持续超时（每次 500ms）填满 `mpsc(50)` 后，reader 停止 `reader.next()`，15 秒 idle 超时检测没机会执行——连接既不报错也不处理心跳/RPC，最多阻塞约 25 秒。和项目"录音线程不等网络"的设计原则相反。
- **修复**：`play()` 用 `try_send`，满时丢帧或 spawn 独立任务，别阻塞 reader。

### 17. 音频编解码路径没有任何会失败的测试
- **位置**：`examples/xiaozhi/tests/`（无 `test_codec.py`）
- 测试覆盖了 VAD、KWS、回声消除、退出词、重连握手，但 `encode_audio` 帧边界/`remain_frames`、`decode_audio` 帧长、`read_audio` 注入覆盖（见 #14）、`send_audio` 异常路径都没有测试。#14 这类字节/帧边界 bug 因此长期存活。
- **修复**：补一个 `test_codec.py`，至少覆盖"注入时 temp_frames 有残留"这一例。

## Verdict（结论）

功能相当完整，测试也比多数家庭项目扎实；但两类问题必须先修：**物理设备误操作**（#1/#4/#8）会真的开关燃气和电视，**长期运行假死/崩溃**（#3/#6/#7）会让小七在无人值守时悄悄失效。先动 #1、#3、#4。

**Lean**：约 -60 行死代码可删（#18）；没有能在不重写前提下移除的依赖。

**Not checked（未查）**：`promo-video*` 宣传视频生成脚本（不参与运行）、`xiaoqi/` 与 `xiaozhi/` 下运行时生成的数据/模型目录、各 `deploy/*.yml` 的实际容器编排行为、需真机验证的回声消除/唤醒率/红外时序。未实际运行系统或其测试，结论均来自静态阅读。
