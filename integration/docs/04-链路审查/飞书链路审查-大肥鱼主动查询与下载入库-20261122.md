# 飞书表格 → 本地知识库链路审查

> 2026-11-22。老张提出「规划中 Hermes 可以主动查询我的飞书表格、下载视频总结到本地知识库」，要求审查。
> 本轮只读调查，未改任何代码、未动任何服务、未触碰飞书表与抖音平台。

## 0. 一句话结论

**方向对，但对 Hermes 能力的描述有三处与事实不符**——这正是融合规划必须纠正的地方：

1. Hermes（大肥鱼）**读不到飞书表格内容**，没有任何工具能读表；它只能驱动 Windows 上的同步桥去读。
2. 「下载视频总结」不是一步到位，是**两段式 + 人工确认闸**：默认 `download=false` 只补元数据，要真下载得显式开 `download=true` 并重启桥，且必须人确认才放行。
3. 整条链路跑在 **Windows 本机**（lark-cli + playwright 真实 Chrome + TokBrain 后端 8001），不是 NAS。**融合规划阶段 3「收敛到 NAS 摆脱 Windows」如果照原样做，会直接掐断这条飞书链路**——这是规划的实质性漏洞。

## 2. 三处说法纠正

### 2.1 「Hermes 主动查询飞书表格」→ 实为「驱动桥间接查询」

Hermes 通过 control MCP 能做的是：`tb_sync_status`（桥在不在跑、队列积压、连哪张表、什么模式）、`tb_sync_pending`（桥预检完、带标题的待确认条目）。**它看不到表的原始行**，更不能自己捞链接——明示禁止 `tb_import_links` 去读表（会双重导入、破坏状态回写）。

「主动」的部分成立：Hermes 可以自己发起 `tb_sync_status/start/pending` 这一串动作。但「查询表格」的主体是 Windows 桥，不是 Hermes。

### 2.2 「下载视频总结到本地知识库」→ 两段式，默认不下载

- 默认 `download=false`：只补元数据、建占位，**不下载视频、不解析**。
- 要真下载：`tb_sync_stop` → `tb_sync_start(download=true)`（换模式必须重启）→ `tb_sync_replay` 重投 → `tb_sync_wait`。
- 预检完停在 `awaiting_confirm`，**必须把标题念给用户听、问一句**，用户点头才 `tb_sync_confirm` 放行。
- 放行后才真抓视频、调 ASR/OCR（花钱、每个视频几分钟），423/429 会熔断 30 分钟。
- 代价说明在 `mcp_control.py:155-160` 写得很直白：防止「手机随手丢链接 = 自动烧额度 + 自动撞风控」。

一道例外：用户明确说过「以后都别问我」，就在**本机**配 `FS_AUTO_CONFIRM=1`，而不是让 agent 跳过闸。

### 2.3 「本地知识库」是 Windows 本地，NAS 上是只读快照

真正的写入发生在 Windows 的 `data/douyin_rag.db`；NAS 上的 `/vol1/1000/tokbrain/data/douyin_rag.db` 是**快照**（scp 过去、chmod 400、只给 Hermes 只读检索）。规划文档 §2「Hermes 读写同一个库」在当前架构下不成立——Hermes 写不了 NAS 那个库，写要绕回 Windows。

## 5. 一个必须点出的安全隐患（衔接开源准备）

读码时发现**明文凭据**：`launchers/启动飞书同步.cmd` 和 `mcp_server/control.env.bak-20261117-233552` 里有
`FEISHU_BITABLE_APP_TOKEN`、`FEISHU_BITABLE_TABLE_ID`、`TOKBRAIN_CONTROL_TOKEN=493574...`（我打码了）。

这些在 `D:/code/TokBrain-main` 仓库内。**如果 TokBrain 也要开源，必须**：

1. 把这两个 token 视为已泄露 → 轮换（飞书表 app token 重置、control token 重签）；
2. 加入开源准备检查清单的 P0 轮换表（现清单只覆盖 xiaoqi/xiaozhi 运行拷贝，未覆盖 TokBrain 仓库）；
3. `*.env.bak*`、含 token 的 `.cmd` 进 .gitignore 或改写为读环境变量。

注：这与上一轮开源准备是**不同的仓库**——当时扫的是 `open-owoqrq-main`，这次暴露的是 `TokBrain-main`，两者都要处理。
